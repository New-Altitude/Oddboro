- [staff] **Decision (2026-11-03): an Odd runs once at a time on a thread. Any follow-up on a thread but a hand-off waits while a run of the same Odd there has yet to end, and claiming one locks the thread. A run on no thread, such as a chat, a job, a draft or a carry-out, is a run there once it puts work on the thread: a hand-off, taken or held for the owner, or a goal's plan. Results that land while the hub runs there wait, and its next pick-up takes them all, names each in its brief and ends them with it; a lone result picks up as before. An answer joins the hub's pick-up while it has yet to start. Every hub run on its thread is told the hand-offs still out, so it can go on with what is back or finish and wait. There is no timer and no wait for all.** A hub may hand off several pieces in one run, and only its `resume` waited, so three results close together started three runs of the hub at once on one thread: double work, a thread settled early, and a raced budget. Answers already joined a waiting `resume` the same way. A hand-off is new work, not a pick-up, so several still run side by side, even for one colleague. A colleague's run on the owner's answer also waits for the run that raised it. On 2026-11-03 the owner ruled that results wait while the hub runs on the thread and join its waiting pick-up. A live trial then found a lead's chat run handing out three pieces while its first result came back: the pick-up started beside the chat, which cost a duplicate hand-off and an extra run. So the office gives every run that is no follow-up a key, its hand-offs carry the key, and the hold counts a hand-off whose key is still going. The keys live only in the office's memory (`runsGoing`), so a restart ends every hold and no pick-up waits forever; a run ending makes the office look again. A review on 2026-11-03 found the hold blind where no hand-off was written: a chat whose new thread waited on a big estimate or on the usage window, a held share, a carry-out on no thread that handed off, and a chat that raised a goal's plan. In each, the owner's yes started the hub beside the run still going. So every run now gets a key, and the thread keeps the key of each of its hub's runs that puts work on it (`threads.runs`, from migration `0002_hand-offs`, written by `keepRun`), in place of the key on each hand-off. A colleague's run keeps none, since a key holds the hub's pick-ups whoever's run it is. The tool server records it from a process of its own, which the office's memory cannot see, so the key goes in the database; which keys still go stays in memory, so an old key holds nothing and none needs clearing. Code in `packages/ledger/src/office-follow-ups.ts` (`waitsOnOwnRun`, `startFollowUp`, `finishFollowUp`), `packages/ledger/src/hand-offs.ts` (`resultsToJoin`, `handOffBrief`), `packages/ledger/src/threads.ts` (`threadBrief`, `keepRun`, `answerThread`) and `apps/office/src/lib/server/staff.ts` (`followThrough`, `run`), with `apps/office/src/lib/server/follow-ups.ts` looking again when a keyed run ends.
