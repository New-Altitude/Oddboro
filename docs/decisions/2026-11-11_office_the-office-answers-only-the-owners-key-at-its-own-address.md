- [office] **Decision (2026-11-11): the office answers only at its own names (127.0.0.1, [::1], localhost, its addresses through Caddy and the app's ORIGIN), and only to a request that carries the owner's key, with exact exception routes that prove themselves another way.** Any program on the computer, and any page open in the owner's browser, can send the office a request with whatever headers it likes, so headers cannot tell the owner from anyone else. The office keeps one key in its folder (`owner-key`, made on first use). The owner's page holds it as the cookie `oddboro-owner-<port>` (SameSite Lax, named by the office's port, since a browser scopes cookies by host and not port), and gets it by opening any page once with `?oddboro-key=<key>`, which the office answers with a redirect to the same address and the cookie. The app's shell, `npm run setup` and the shell's new windows on the office's own origin open with it. Without the key a request, a read included, reaches only an exact exception route: `/api/update` with the shell's token, `/api/gateway/<id>` with a run's token, GET or HEAD on the two sign-in callback pages with their own sign-in state, and GET or HEAD on `/api/office-proof`, which changes nothing and answers only an HMAC of the key over a fresh nonce and the listener the request came through (the office itself, or its Caddy by scheme, which Caddy marks with a header holding a hash of the key). The path is judged on the text the server routes on. SvelteKit decodes that text before it routes, and no exception route or route parameter matches a `%`, so text that passes reads the same once decoded and the guard and the router agree. No request carrying the key, as the cookie or in the address, goes to an address this run has not proven is this office: every address its name resolves to must be 127.0.0.1 or ::1, and each must answer a fresh nonce with that HMAC for the listener expected, so a program that took a port the office uses never gets the key. The office holds both 127.0.0.1 and [::1] on its port, so no other program can sit on the other one and pass the proof on to it. With the key, an action (anything but GET, HEAD or OPTIONS) must also come from the owner's own page, told apart by what the browser says (Sec-Fetch-Site, or with none an Origin naming the host asked), because a page on another localhost port is same-site and carries the cookie too. In dev, a first Vite plugin applies the same rule ahead of Vite's own routes and its websocket, and Vite's `/__open-in-editor` is refused outright. Limits: the key does not keep out every program on this computer. A program running as the owner can read the key, as it can read the database beside it. And a browser scopes cookies by host, not by port. So once the browser holds the key for a name, it sends the key to whatever already holds, or later holds, port 80 at that name, and any page can start that visit. https with a Secure cookie is the full fix, and a tracked follow-up. The key also appears in the browser's history as the address before the redirect, and in the system opener's arguments (`open` on a Mac, `xdg-open` on Linux, `rundll32` on Windows) once each time `npm run setup` opens the office, and each time the app's shell opens a new window on the office's own origin in the default browser; the shell's own window gets it through its own address, not the opener. Code in `packages/ledger/src/owner-key.ts`, `packages/ledger/src/office-proof.ts`, `apps/office/src/lib/server/owner-page.ts` (`guardOffice`) and `apps/office/vite.config.ts` (`ownerOnly`, `noEditorLaunch`); supersedes the 2026-11-04 ruling.
