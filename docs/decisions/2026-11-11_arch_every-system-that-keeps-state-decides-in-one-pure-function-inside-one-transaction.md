- [arch] **Decision (2026-11-11): every system that keeps state decides each change in one pure function inside one transaction, and its rules are tested with random event sequences.** The owner ruled on 2026-11-11 that every stateful system gets one core and random-sequence tests, so a change is decided in one place, from the rows it holds, and a rule broken by some order of events shows up in a test before it reaches an office. The shell (`transition` in `packages/ledger/src/transition.ts`) loads the rows a change needs and locks them in `LOCK_ORDER`, asks a pure decider (no database, no clock), and writes what it decides, in one transaction; ledger lines and other effects wait for the commit, and a deadlock runs it again from the load. The office's work is one such system: each thing that can happen to it is an event (`WorkEvent` in `packages/ledger/src/work/events.ts`) with exactly one decider (`DECIDERS` in `work/decide.ts`), and every entry hands its event to `transitionWork` (`work/apply.ts`). Each stored thread, follow-up, ask and task is read by a parser into one state its type allows, which refuses a row whose columns disagree (`RowNotParsed`), and written back whole by a serializer (`work/state.ts`). Database checks hold the same rules on every new write (migration `0030_work_checks`), `NOT VALID` so a row an office already holds never stops the upgrade. Tests drive the deciders through seeded random event sequences (`explore` in `packages/ledger/src/sequences.ts`, which shrinks a failure to its shortest form): a test keeps its own record of what is true, built only from the events, and says each rule as an equality between that record and the system, never as a bound. The lessons take the same shape (`decideLesson` in `packages/ledger/src/lesson-rules.ts`), under a lock per lesson scope (`lockScopes` in `lessons.ts`). On the page an Odd's live state is derived once (`oddNow` in `apps/office/src/lib/staff/odd-now.ts`), so the floor, the card, the rail and the info page cannot disagree, and it has a random-sequence test of its own. A new system that keeps state takes the same shape: `docs/architecture.md`, under "A system that keeps state". `packages/ledger/test/pure-modules.test.ts` fails a decider module that loads the database.
